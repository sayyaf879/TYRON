# Confirmation-Gated Self-Mutation: A Safety Pattern for Self-Modifying AI Agents

**Status:** Working implementation, extracted from a personal AI assistant project (TYRON)

## Abstract

Autonomous agents that can modify their own source code are usually
discussed as either a research curiosity or a safety hazard. This paper
describes a small, concrete pattern — **propose → sandbox-test → backup →
apply → rollback**, with a mandatory human approval step before any
change touches production code — that makes self-modification practical
and safe enough for a single-user personal assistant running on real
hardware with real system access (code execution, file operations,
device control).

The core claim is narrow and testable: an agent that generates code
changes for itself does not need to be trusted to be useful, as long as
every change passes through an isolated test environment and a human
approval gate before it can take effect, and every change is trivially
reversible.

## The Problem

Most demonstrations of "self-improving AI" either:

1. Apply changes directly with no test step (a bad idea — untested code
   generated by an LLM will sometimes be wrong), or
2. Never actually apply changes at all — the "self-improvement" is
   simulated or requires a full manual review-and-merge cycle indistin-
   guishable from a human writing the code themselves, which defeats the
   point of automation.

Neither extreme is useful for a personal assistant that runs continuously
and has real capabilities (executing code, controlling a mouse/keyboard,
running shell commands).

## The Pattern

```
Propose (LLM) -> Sandbox Test -> Human Approval -> Backup -> Apply
                                                                 |
                                                          Rollback (if needed)
```

**1. Propose.** An LLM (in this implementation, triggered during idle
periods by scanning trending open-source repositories for techniques
relevant to the agent's own stack) generates a complete replacement for
one existing source file, plus a one-line natural-language description of
what changed and why.

**2. Sandbox test.** The proposed file is written to a temp location and
executed as a subprocess with a timeout. This catches syntax errors,
import failures, and immediate runtime exceptions before the code goes
anywhere near the live system. A patch that fails this step is discarded
automatically — it never reaches the human.

**3. Human approval.** Only patches that pass the sandbox test are
surfaced to the user, framed as: what was discovered, what would change,
and confirmation that the test passed. Nothing is applied without an
explicit approval action.

**4. Backup.** Immediately before writing the new code over the old, the
original file is copied to a timestamped backup location.

**5. Apply.** The new code replaces the old file.

**6. Rollback.** At any point, the most recent backup for a given file
can be restored with a single call — no manual archaeology through git
history required (though this doesn't replace version control; it's a
faster, agent-triggered undo).

## Why This Is Different From "The Agent Has Full Autonomy"

The agent never has unsupervised write access to its own running code.
Every step up to and including the sandbox test is fully autonomous —
the agent can propose and validate changes with zero human involvement,
which is where most of the actual work (search, generation, testing)
happens. But the step that matters for safety — *does this change take
effect* — always requires a human in the loop. This is a deliberate
asymmetry: automate the expensive part (finding and validating good
changes), gate the risky part (making them real).

## Implementation Notes

- The sandbox test is a subprocess with a timeout, not a full container —
  sufficient for catching syntax/import/immediate-crash errors, not a
  security boundary against a maliciously adversarial code generator.
  This pattern assumes the LLM generating patches is not adversarial
  (i.e., this is a safety-against-mistakes pattern, not a safety-against-
  attack pattern).
- Backups are timestamped and kept indefinitely by default; a production
  version should add retention limits.
- The "propose" step in this implementation is opportunistic (idle-time
  triggered, inspired by scanning external repositories for relevant
  techniques) but the pattern works identically if patches are proposed
  for any other reason (a failing test, a user bug report, a scheduled
  audit).

## Reference Implementation

A minimal, dependency-light Python implementation of this pattern is
included in this repository (`self_mutation.py`). It has no dependencies
beyond the Python standard library and implements all five steps
described above as plain methods on a single class.

## Limitations

- Single-file patches only — no support for coordinated multi-file
  changes in this minimal version.
- The sandbox test only catches errors that manifest on file execution
  (syntax errors, import failures, crashes in module-level code) — it
  does not run the target file's actual test suite, since the pattern is
  designed to be generic across any Python file, not tied to a specific
  testing framework. A production deployment should extend the test step
  to run the relevant test suite for the changed file.
- Trust in the pattern depends entirely on the human approval step being
  taken seriously — it provides no protection if approvals are granted
  automatically or without review.
